# Backend Implementation Plan — MemoryChain

## 1. Architecture Overview

The backend is a **stateless Hono API server** that acts as the orchestration layer between the Next.js frontend, IPFS, AI providers, and Arbitrum Stylus smart contracts. It does **not** store user data — Redis is used only for ephemeral session state (session key validation, rate limiting, request deduplication).

### Core Principle: Zero-Knowledge Backend

The backend never sees:
- Plaintext recovery codes
- Raw `K_data` (data encryption keys)
- Unencrypted user data at rest

All encryption/decryption happens **client-side in the browser**. The backend handles:
- IPFS pinning/retrieval of already-encrypted blobs
- On-chain contract calls (credit consumption, metadata writes)
- AI provider proxying with decrypted memory content (received per-request, never stored)
- Session key validation for gasless operations

## 3. IPFS Layer (`lib/ipfs.ts`)

### Strategy: Pinata Primary, Kubo Fallback

Use **Pinata** for production pinning (reliable, pinning service with pin/unpin API). Use **kubo-rpc-client** as fallback for local dev node IPFS.

```typescript
// Pinata config from env
PINATA_API_KEY, PINATA_SECRET_KEY, PINATA_GATEWAY

// IPFS operations
pin(data: Buffer, name: string): Promise<{ cid: string, hash: string }>
retrieve(cid: string): Promise<Buffer>
unpin(cid: string): Promise<void>
```

### What Gets Pinned

The backend receives **already-encrypted** data from the frontend. The flow is:

1. Frontend encrypts data with `K_data` → produces ciphertext
2. Frontend encrypts `K_data` with `K_wallet` → produces wallet envelope
3. Frontend sends to backend: `{ ciphertext, walletEnvelope, recoveryEnvelope, metadata }`
4. Backend pins ciphertext to IPFS → returns CID
5. Backend stores envelopes + CID on-chain via contract calls

### CID + Hash Generation

- CID: Generated by IPFS (content-addressed)
- Hash: SHA-256 of the ciphertext, computed by the frontend before upload, verified by the backend

## 4. Smart Contract Integration (`lib/contracts.ts`)

### Viem Clients

Use `viem` with the `arbitrumNitro` chain config (chain ID 412346). The backend acts as a **read/write proxy** — it submits transactions on behalf of users using session keys or relay patterns.

### Contract Addresses (from deployment)

| Contract | Address |
|----------|---------|
| CreditManager | `0xac3b...c348` |
| UserRegistry | `0xb66f...555c4` |
| MemoryRegistry | `0x7696...2eda` |
| AgentRegistry | `0xcb59...f94e` |
| ContextRegistry | `0x9e60...acc2` |
| AuditRegistry | `0xa3ba...aa26` |

### Contract Call Pattern

The backend needs to call contract functions that require the user's authority. Two patterns:

**Pattern A: Frontend-signed transactions** (for initial setup, recovery)
- Frontend signs the transaction with the wallet directly
- Backend only reads contract state

**Pattern B: Session key execution** (for normal operations)
- User grants ERC-7715 permission scoped to specific contract calls
- Backend holds the session key and submits UserOperations
- Smart account validates the session key against granted permissions

### Key Contract Calls the Backend Makes

| Operation | Contract | Function | Auth Required |
|-----------|----------|----------|---------------|
| Check credit balance | CreditManager | `balanceOf(user)` | None (view) |
| Check sufficient credits | CreditManager | `hasSufficientCredits(user, amount)` | None (view) |
| Get operation fee | CreditManager | `getFee(operation)` | None (view) |
| Consume credits | CreditManager | `consumeCredits(user, amount)` | Session key |
| Create memory | MemoryRegistry | `createMemory(cid, hash, type, vis)` | Session key |
| Update memory | MemoryRegistry | `updateMemory(id, cid, hash)` | Session key |
| Create agent | AgentRegistry | `createAgent(name, desc, cid, hash)` | Session key |
| Update agent | AgentRegistry | `updateAgent(id, cid, hash)` | Session key |
| Link memory | ContextRegistry | `linkMemory(agentId, memoryId, priority)` | Session key |
| Create chat | ChatRegistry (TBD) | `createChat(name, agentId, cid, hash)` | Session key |
| Update chat | ChatRegistry (TBD) | `updateChat(id, cid, hash)` | Session key |

## 5. AI Provider Proxy (`lib/ai-providers.ts` + `routes/chats.ts`)

### Provider Configuration

Use Vercel AI SDK (`ai` package) with provider-specific adapters:

```typescript
import { openai } from '@ai-sdk/openai';
import { anthropic } from '@ai-sdk/anthropic';
import { google } from '@ai-sdk/google';

// Provider registry
const providers = {
  openai: openai(process.env.OPENAI_API_KEY),
  anthropic: anthropic(process.env.ANTHROPIC_API_KEY),
  google: google(process.env.GOOGLE_API_KEY),
};
```

### Memory Injection Flow

When a user sends a chat message:

1. Backend receives: `{ agentId, message, provider, model }`
2. Backend queries ContextRegistry to get all linked memory IDs for this agent
3. For each linked memory, backend fetches the CID from MemoryRegistry
4. Backend fetches encrypted content from IPFS
5. Frontend has already decrypted and sent the memory content in the request (or the backend receives decrypted memory context from the frontend)
6. Backend assembles the system prompt with full memory content
7. Backend streams the AI response back via SSE
8. Backend consumes credits on-chain after successful response

**Critical**: Step 6 — the decrypted memory content is sent by the frontend in the request body. The backend does NOT decrypt. The frontend decrypts client-side and sends the plaintext memories as part of the chat request.

### Streaming Response

Use Server-Sent Events (SSE) for AI response streaming, compatible with `@assistant-ui/react`:

```
POST /api/chats/:chatId/messages
→ SSE stream with text deltas, tool calls, reasoning
```

## 6. Credit Consumption Flow

### Pre-paid Model

Every AI operation consumes credits **before** the API call:

```
1. Frontend sends chat message
2. Backend checks: hasSufficientCredits(user, providerFee) → if false, return 402
3. Backend calls: consumeCredits(user, providerFee) → on-chain tx
4. Backend proxies to AI provider
5. Backend streams response to frontend
```

### Provider Fee Configuration

Store per-provider/model fees in a config file (not on-chain — these are backend operational costs, not protocol fees):

```typescript
// lib/credits.ts
const AI_FEES: Record<string, number> = {

```

### Credit Balance Check Endpoint

Frontend polls or subscribes to credit balance for UI display:

```

```

## 7. Session Key Management (`lib/session-keys.ts` + `routes/session-keys.ts`)

### ERC-7715 Integration

Session keys use the ERC-7715 standard (`wallet_grantPermissions`). The flow:

1. **Grant**: Frontend calls `wallet_grantPermissions` via the user's wallet
2. **Store**: Frontend sends the `permissionsContext` + session key private key to the backend
3. **Validate**: Backend stores session key in Redis with TTL matching the permission expiry
4. **Execute**: Backend uses the session key to sign UserOperations for contract calls
5. **Revoke**: Frontend calls `wallet_revokePermissions`, backend deletes from Redis

### Session Key Scope (for MemoryChain)

The granted permissions should cover:

```typescript
const MEMORYCHAIN_PERMISSIONS = [
  {
    type: 'contract-call',
    data: {
      target: CREDIT_MANAGER_ADDRESS,
      selectors: ['consumeCredits(address,uint64)'],
    },
  },
  {
    type: 'contract-call',
    data: {
      target: MEMORY_REGISTRY_ADDRESS,
      selectors: ['createMemory(string,bytes32,uint8,uint8)', 'updateMemory(bytes32,string,bytes32)'],
    },
  },
  {
    type: 'contract-call',
    data: {
      target: AGENT_REGISTRY_ADDRESS,
      selectors: ['createAgent(string,string,string,bytes32)', 'updateAgent(bytes32,string,bytes32)'],
    },
  },
  {
    type: 'contract-call',
    data: {
      target: CONTEXT_REGISTRY_ADDRESS,
      selectors: ['linkMemory(bytes32,bytes32,uint8)', 'unlinkMemory(bytes32,bytes32)'],
    },
  },
  // ChatRegistry selectors (TBD)
];
```

### Redis Storage

```
Key: session:{userAddress}:{sessionKeyId}
Value: {
  sessionKeyAddress: string,
  permissionsContext: string,
  expiry: number,
  scopes: string[],          // allowed function selectors
  grantedAt: number,
}
TTL: matches permission expiry
```

### Session Key Validation Middleware

Every protected route checks:
1. Is there a valid session key for this user in Redis?
2. Does the requested operation match the session key's scope?
3. Has the session key expired?

If no valid session key → return 401 with `REQUIRE_WALLET_SIGN` error.

## 8. Recovery Flow (`routes/recovery.ts`)

### Client-Side Re-keying

The recovery flow is **entirely client-side**. The backend's role is minimal:

1. User enters recovery code in the browser
2. Frontend derives `K_recovery` from the code
3. Frontend fetches encrypted envelopes from IPFS (via backend GET proxy)
4. Frontend decrypts `K_data` using `K_recovery` in-browser
5. Frontend signs authorization message with new wallet → derives `K_wallet_new`
6. Frontend encrypts `K_data` with `K_wallet_new` → new wallet envelope
7. Frontend sends to backend: `{ itemId, itemType, newCid, newHash, newWalletEnvelope }`
8. Backend updates on-chain metadata (CID + hash) via contract call with new wallet's signature

### Backend Endpoints for Recovery

The backend provides two recovery-related endpoints:

- `POST /api/recovery/re-key` — Receives new CID + hash + wallet envelope, updates on-chain metadata
- `POST /api/recovery/verify` — Verifies the recovery code derives a valid key (optional, for UX)

Both require the **new wallet** to sign the session key grant, ensuring the user has control of the new wallet.

## 9. Session & Auth (`middleware/session.ts`)

### SIWE (Sign-In with Ethereum)

Use `siwe` + `iron-session` for backend session management:

1. **Challenge**: Frontend requests a SIWE message to sign
2. **Verify**: Frontend sends signed message + wallet address
3. **Session**: Backend creates an iron-session cookie with wallet address
4. **Subsequent requests**: Session cookie authenticates the user

### Session Data

```typescript
interface SessionData {
  address: string;           // wallet address
  chainId: number;           // chain ID (412346 for ArbitrumNitro)
  username?: string;         // from UserRegistry
  sessionKeyId?: string;     // active session key ID (if any)
}
```

### Session Expiry

- Default session: 24 hours
- Session key session: matches the ERC-7715 permission expiry

## 10. Redis Usage

Redis is used **only** for ephemeral state:

| Key Pattern | Purpose | TTL |
|-------------|---------|-----|
| `session:{sessionId}` | SIWE session data | 24h |
| `session-key:{address}:{keyId}` | Active session key + scopes | Permission expiry |
| `rate:{ip}:{route}` | Rate limiting counters | 1h |
| `challenge:{address}` | SIWE challenge nonce | 5min |
| `chat-stream:{chatId}` | Active stream state | 30min |

**No business data is stored in Redis.** All persistent data lives on-chain (IDs, names, CIDs) or in IPFS (encrypted content).

## 11. Error Handling

All errors follow a consistent shape:

```typescript
interface ApiError {
  code: string;              // e.g., 'INSUFFICIENT_CREDITS', 'SESSION_KEY_EXPIRED'
  message: string;           // human-readable
  details?: Record<string, unknown>;  // optional context
}
```

### Error Codes

| Code | HTTP Status | Meaning |
|------|-------------|---------|
| `AUTH_REQUIRED` | 401 | No valid session |
| `SESSION_KEY_EXPIRED` | 401 | Session key TTL exceeded |
| `SESSION_KEY_SCOPE` | 403 | Operation not in session key scope |
| `INSUFFICIENT_CREDITS` | 402 | Not enough MC for operation |
| `IPFS_PIN_FAILED` | 502 | IPFS pinning service error |
| `IPFS_RETRIEVE_FAILED` | 502 | IPFS retrieval failed |
| `CONTRACT_REVERTED` | 500 | On-chain transaction failed |
| `PROVIDER_ERROR` | 502 | AI provider returned error |
| `VALIDATION_ERROR` | 400 | Request body failed Zod validation |
| `RATE_LIMITED` | 429 | Too many requests |

## 15. Key Tradeoffs

| Decision | Choice | Rationale |
|----------|--------|-----------|
| IPFS pinning service | Pinata (primary) | Reliable, good DX, pin/unpin API. Kubo fallback for local dev. |
| Memory delivery to AI | Frontend sends decrypted memories in request | Backend never sees plaintext at rest. Decryption is client-side. Backend just injects into prompt. |
| Credit consumption | Pre-paid (before AI call) | Prevents cost runaway. Slight latency hit but worth it for solvency. |
| Session key storage | Redis (ephemeral) | No persistent DB needed. TTL matches permission expiry. |
| AI streaming | SSE via Vercel AI SDK | Compatible with assistant-ui/react. Standard pattern. |
| Recovery | Client-side re-keying | Security-critical — recovery code never leaves browser. Backend only updates metadata. |
| Contract calls | Session key execution | Avoids requiring user signature on every operation. ERC-7715 scoped. |
